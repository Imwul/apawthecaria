## 🎯 Design Challenge

숲속 약제사의 여행·진료·채집·조제가 관리 화면처럼 보이고, 현재 상황에서 해야 할 일을 여러 기능과 원문 사이에서 연결해야 한다. 장식만 더하면 작업이 더 멀어진다. 분위기와 개성을 만들면서 현재 행동·부족 조건·비용·결과를 실제 workspace에서 함께 보여주는 구조가 필요하다.

성공은 사용자가 요구한 시각 교체와, 첫 진입부터 중단 후 재개까지 실행 가능한 흐름을 함께 충족하는 것이다. 서사적 선택은 플레이어가 작성하며, 자동화할 수 없는 원문 후속 결과는 저장 가능한 직접 판정으로 남긴다.

### Key Observations

코드·브라우저에서 확인한 사실과 가설을 구별한다.

1. 교체 전에는 9개 일지 탭, 영구 프로필·통계 sidebar와 반복된 장 표지가 있었다. 상태 기반 계속하기와 캠페인 연속성은 이미 구현돼 있었다.
2. 생성·여정·이동·환자·채집·흥정·조제·저장 기능은 풍부하다. 실행 기능이 모두 없다는 주장은 하지 않는다.
3. 감사에서 Replacement를 일반 약재 획득에 덧붙이는 경로, 사용자 정의 약재 조제 단절, 곰 영주의 별도 회분 차단 등 구체적인 실행 결함을 확인했다. 근거는 `design-thinking-play-audit-2026-10-03.md`에 보존한다.
4. 진료와 병증 참고의 이름·목적지, 복수 질환의 시간 의미, CTA·길잡이·실제 행동 우선순위에 차이가 있었다.
5. 번호 입력 native prompt, 모바일에서 보이지 않는 판정 사유, 클라우드 용량의 console 경고가 실제 코드에 있었다.
6. 현재 entry는 `index.css` 뒤 `workspace.css`를 사용한다. 초기 forest/adventure CSS·SVG·SUITE는 현재 렌더 기준에서 제외된다.
7. 이전 QA 결과는 당시 구현에 대한 증거다. 최신 변경의 검증 결과로 재사용하지 않는다.

가설: 상단의 이름 있는 5개 도구와 명시적 추가 메뉴가 모바일 기능 발견을 돕는다. 작은 분위기 이미지가 큰 표지보다 작업 진입을 빠르게 한다. 짧은 조건·비용 설명이 외부 룰북 참조를 줄인다. 이 효과의 크기는 사용자 관찰로 측정하지 않았다.

### Empathy Map Summary

**Says:** 전면 교체, 룰북 없이 진행, 토의와 자율 실행. 초기 그림과 서체에 대한 거절도 실제 요구다.

**Thinks — 가설:** “지금 처방에 무엇이 부족하지?”, “이 버튼이 어떤 시간을 쓰지?”, “보류한 장면은 어디서 이어가지?”

## 🎨 DEFINE: Frame the Problem

### Point of View Statement

처음 하거나 돌아온 솔로 플레이어는 현재 상태에서 필요한 행동, 조건과 결과를 한 흐름으로 읽어야 한다. 규칙과 작업이 흩어지거나 같은 말이 다른 화면으로 연결되면 약제사의 여행보다 앱 조작에 신경을 쓰게 된다.

### How Might We Questions

- 어떻게 분위기를 만들면서 실제 처방과 행동을 먼저 보이게 할까?
- 어떻게 현재 진료와 병증 참고의 목적지를 명확히 구별할까?
- 어떻게 부족 약효→획득→조제→소비→기록을 끊김 없이 연결할까?
- 어떻게 달력과 질환별 치료 시간을 혼동 없이 설명할까?
- 어떻게 보류·reload·키보드 재개를 같은 저장 상태로 이어갈까?
- 어떻게 도움말을 기본 접힌 상태에서도 필요할 때 찾게 할까?
- 어떻게 원문 모호성과 실제 오구현을 구별해 안내할까?

### Problem Reframing

초기에는 수작업 숲 그림과 색으로 기존 기록 공간의 개성을 강화하려 했다. 사용자 피드백과 감사 이후 문제를 **현재 작업을 먼저 보여주고 실제 실행 단절을 해소하는 전면 재구성**으로 다시 정의했다. 고정 레일이나 큰 장면을 보존하는 것은 요구가 아니다. 상태·규칙·저장 계약을 보존하면서 화면의 구조를 바꾼다.

적용 방법: **Point of View, How Might We, Five Whys**. 원인 가설을 코드 사실과 구분했다.

## 🛠️ PROTOTYPE: Make Ideas Tangible

### Prototype Approach

**Storyboarding, Role Playing, Rapid Prototyping**을 적용했다. 실제 React 화면·CSS·이미지·서체와 저장되는 게임 흐름으로 구현하고 로컬 preview에서 확인한다. 장식 mockup만 완료로 취급하지 않는다.

### Prototype Description

- `JournalExperience.tsx`: 상단 주 도구·자료/기록 메뉴, 현재 단계·이유·주 CTA·환자 strip, 접힌 여정/기록. 분위기 이미지는 데스크톱 오른쪽, 모바일에서 숨긴다.
- `App.tsx`: compact header, 8단계 생성 재배치, 실제 작업 재개, 병증 사전과 현재 진료 구별, 설정의 백업/불러오기/초기화. native prompt 입력은 controlled 선택으로 전환한다.
- `workspace.css`: 현재 색·언어별 서체·상단 탐색·모바일 작업 공간의 기준. entry는 `index.css` → `workspace.css`다. 초기 forest/adventure CSS는 로드하지 않는다.
- `woodland-pigment.jpg`: 현재 회화 이미지. 기존 SVG 두 개와 SUITE는 초기 제안 자료이며 현재 화면에 사용하지 않는다.
- `PlayGuide`, `playGuide.ts`: 9개 화면 절차·첫 플레이 5단계·19개 검색 용어. 도움말은 기본 접힘이며 현재 행동 projection을 공유한다.
- `useDialogFocus`, `FocusDialog`, `EncounterReadiness`: 키보드 진입·순환·배경 inert·복귀, Escape 보류, 판정 전 부족 입력과 이동 버튼.
- `cloudCapacity`, `CloudSaveCapacityNotice`: UTF-8 크기·한도·기기 보존과 JSON 백업/복구 안내. 로컬 저장을 먼저 보존한다.

## ✅ TEST: Validate with Users

### Testing Plan

현재 검증은 자동 테스트와 에이전트의 코드/브라우저 점검이다. 실제 초보 사용자 과제 관찰·만족도·이해도 측정은 하지 않았다.

후속 사용자 과제: 초보자 3~4명과 익숙한 사용자 2~3명에게 절차를 미리 설명하지 않고 첫 여정과 치료를 수행하게 한다. 외부 룰북을 찾은 횟수, 막힌 위치, 왕복한 화면, 시간·약효 이해를 관찰하고 **Feedback Capture Grid**로 좋아한 점·질문·새 아이디어·변경 요청을 나눈다. 이 과제는 계획이며 수행 결과가 아니다.

### User Feedback

직접 요구·통합 담당을 통해 전달된 피드백은 기존 디자인 불만, 자율 진행, 기존 패러다임 교체, 초기 선 손그림·SUITE 거절, 감사27 제외 수정 승인, 럭셔리 고딕과 좁고 길쭉한 한글 요청이다. 이를 따라 화면 구조와 시각 방향을 다시 선택했다. 새 UI의 만족도 점수나 초보자의 무도움 치료 성공률은 없다.

### Key Learnings

- 기존 상태·버튼을 설명과 연결할 수 있지만 실제 실행 단절은 엔진과 소비 경로까지 수정해야 한다.
- 미적 참고를 곧바로 특정 SVG·서체의 승인으로 간주하면 안 된다. 사용자 피드백으로 선택을 바꿨다.
- 복수 시간, 진료/자료, mandatory/optional 규칙을 구별하면 현재 설명을 더 정확하게 만들 수 있다.
- 과거 완성 표와 단위 데이터 존재는 새로운 UI와 획득·치료 종단 검증을 대신하지 않는다.
