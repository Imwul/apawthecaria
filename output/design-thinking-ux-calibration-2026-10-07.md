# Apawthecaria — UX Calibration

날짜: 2026-10-07 · 기준: Preserve the identity. Reduce the friction.

실행 중인 Field Station 디자인을 기준으로 관찰하고 수정했다. 작업 시작 전에 존재하던 디자인 개편과 미커밋 변경을 보존했다. 이번 작업의 변경은 제품 코드 3개 파일과 기존 테스트의 문구 검사 1개다. 배포나 저장 데이터 마이그레이션은 하지 않았다.

## 1. Product Understanding

이 앱은 카드 기반 Apawthecaria를 혼자 진행하는 플레이어의 약제사 일지다. 핵심 행동은 약제사·길동무 생성, 여정 준비와 이동, 환자 진단, 약효와 재료 비교, 채집·거래·조제, 결과와 개인 서사 기록이다. 규칙 계산과 기록 보관을 지원하면서, 여행 이유와 기억은 플레이어가 직접 남긴다.

직접 수행한 작업은 다음과 같다.

| 작업 | 선택 → 실행 → 결과 → 다음 행동 |
|---|---|
| 첫 기록 만들기 | 카드·동물 선택 → 약제사 시트 저장 → 작업 화면 → 여정 준비 |
| 약재 찾기 | Marigold 검색 → 표본 선택 → 부위·약효·도구 확인 → 관련 원문 열기 |
| 처방에서 재료 찾기 | Monthly Chore 펼치기 → SCALE 재료 찾기 → 재료 목록 → 표본 비교 |
| 이야기 남기기 | 제목·본문 작성 → 질환 사전 왕복 → 초안 복귀 → 저장·기록 확인 |
| 여정 시작 | Obridge 선택·직접 목표 입력 → 이유 작성·출발 → 0/12일 여정 → 경로 짜기 |
| 모바일 작업 왕복 | 펼친 처방 → 기록 모드 → 찾기 모드 → 같은 처방 재개 |

첫 사용자는 카드 여섯 장과 실제 동물·이름을 정한다. 기존 캠페인 사용자는 현재 작업과 남은 절차를 먼저 확인한다. 반복 행동은 진행 화면, 재료, 질환, 지도, 배낭, 이야기 사이의 왕복이다. 반복 빈도 평가는 이 작업 모델에 대한 판단이며 실제 사용량 통계는 아니다.

실제 사용자 인터뷰나 모집된 참가자 테스트는 없었다. 사용자 감정·인지에 대한 설명은 직접 사용 관찰로 만든 가설이며, 인간 사용자의 발언이나 만족도 결과로 제시하지 않는다.

## 2. Existing Design Language

기존 DESIGN_SYSTEM.md의 Forest Folio 설명보다 실제 실행 화면과 현재 CSS, 앞선 Field Station 작업 기록을 기준으로 삼았다. 이전 스타일을 되살리는 작업은 하지 않았다.

| 영역 | 보존할 언어와 동작 |
|---|---|
| 색·표면 | 짙은 녹회색 레일 `#263330`, 따뜻한 종이 `#faf9f5`, 보조 표면 `#eeeae2`, 잉크 `#25332f`, 주 행동의 녹슨 붉은색 `#ad482e` |
| 글꼴 | Instrument Serif 워드마크, Freesentation 한국어 본문·조작, 수치·색인의 monospace |
| 배치 | 데스크톱 232px 레일, 본문 최대 1280px, 40px 여백. 작은 화면은 기존 두 줄 모드/목적지 탐색 |
| 정보 구조 | 여행·찾기·기록 3그룹, 9개 목적지. 번호와 분리선으로 구성된 작업 색인 |
| 밀도·리듬 | 설명을 필요할 때 펼치고, 이름·기한·약효를 비교하는 대장 형태. 데이터와 서사 문장의 역할 구분 |
| 컴포넌트 | 기존 버튼·입력·`workspace-link`, 44px 조작 영역, native details, 기존 상태·결과·대화상자 |
| 상호작용 | 활성 목적지, 검색·필터·표본 선택, 키보드 포커스, 원문 drawer, hash 탐색과 브라우저 Back |
| 도감 | 데스크톱 목록/상세 분할, 모바일 선택 상세를 목록보다 먼저 제시 |

이 제품의 특징은 여행 일지의 문장과 진료·채집의 수치를 함께 다루는 현장 작업소라는 점이다. 현재 작업 안내, 직접 접근 가능한 자료·기록 색인, 약재 비교, 서사와 판정 결과의 구분은 보호 대상으로 기록했다.

이미 잘 작동한 점도 확인했다. 이야기 제목·본문은 다른 작업에 갔다 돌아와도 유지됐다. 도감 상세에서 원문과 관련 기록을 열 수 있었고, Escape로 닫으면 원래 버튼으로 포커스가 돌아왔다. 접힌 질환 목록의 기한 비교와 native details의 키보드 동작도 유지할 가치가 있었다.

## 3. Before Audit

코드를 고치기 전에 브라우저에서 캠페인을 만들고 아래 작업을 수행했다. 1280×720 데스크톱과 390×844 모바일을 주 비교 조건으로 사용했다. 360×800, 820×1180에서도 관련 화면을 확인했다.

측정 단위는 사용자가 선택한 의미 있는 조작 1회다. native select의 옵션 선택은 1회로 계산하며 메뉴를 여는 내부 클릭, 스크롤, 도구 호출 횟수는 더하지 않는다. 시작 조건이 다른 작업끼리 클릭 수를 비교하지 않았다. 인간 사용자의 작업 시간은 측정하지 않았다.

| 대표 작업·시작 조건 | 수정 전 관찰 | 조작·입력·이동 |
|---|---|---|
| 펼친 Monthly Chore에서 SCALE 재료 찾기. 도감에 이전 `Marigold` 검색이 남아 있음 | 영약재로 이동 → SCALE 선택 → 결과 0개 → 전체 도감 보기 → SCALE 재선택 → 10개 | 조작 4, 새 문자 입력 0, 화면 이동 1, Back 0, 빈 결과 우회 1 |
| 모바일에서 펼친 Monthly Chore → 기록 → 찾기 | 찾기 모드가 첫 목적지인 영약재로 돌아감. 질환 사전을 다시 누르고 같은 상세를 다시 펼침 | 조작 4, 화면 이동 3, 재펼침 1, Back 0 |
| 이야기 제목·본문 입력 → 질환 사전 → Back | 두 입력 모두 유지됨 | 최초 입력 2, 반복 입력 0, 화면 이동 2, Back 1 |
| Marigold 검색 → 표본 → 원문·관련 기록 | 필요한 부위·도구·관련 자료를 기존 상세에서 확인 가능 | 검색 입력 1. 탐색 동작은 변경 대상에서 제외 |
| 여정의 목적지·목표 선택 후 이유 없이 출발 클릭 | 마지막 클릭 후 “이번 여정을 떠나는 이유를 기록해주세요.” 안내창. 입력란에는 필수 표시가 없음 | 정상 작성에 필요한 입력은 그대로이나, 미리 예상하기 어려운 안내창 복귀 발생 |
| 1280×720 레일에서 첫 목적지 찾기 | 브랜드 설명 하단 118.64px, 탐색 시작 76px. 글자가 탐색 영역과 42.64px 겹침 | 목록을 읽을 때 위계·가독성 저하 |

첫 기록 생성에서는 카드 유형과 실제 동물/외형이 별도 항목인데, “필수 선택 6/6”만으로는 모든 필수 항목의 완성을 알 수 없었다. 최종 확인의 누락 항목 버튼은 해당 단계로 정확히 돌아갔다. 전체 생성 흐름을 바꾸기보다 이 불일치를 후속 과제로 남겼다.

요구 약효를 기억해서 다른 화면의 필터에 옮기는 과정, 이전 검색 때문에 생기는 빈 결과, 모바일의 목적지·펼침 상태 상실이 반복 탐색의 주된 마찰이었다. 단순한 미적 취향은 수정 근거로 사용하지 않았다.

## 4. Prioritized Problems

A=작업, B=정보, C=상호작용, D=읽기·탐색을 방해하는 시각 문제, E=반응형 문제. 빈도·심각도·인지 비용·구현 위험은 관찰에 근거한 정성 판단이다.

| 우선순위·분류 | 문제 | 빈도 | 심각도 | 인지 비용 | 조작 비용 | 구현 위험 |
|---|---|---|---|---|---|---|
| HIGH · A/B | 처방에서 도감으로 약효를 수동 전달하고 이전 검색 때문에 0개 결과로 우회 | 처방/재료 비교마다 | 필요한 정보 탐색 방해 | 약효 기억·필터 원인 추론 높음 | 사례 4회 | 낮음: 기존 도감 연결 |

| MEDIUM · A/C | 다른 화면 방문 후 같은 처방을 다시 펼침 | 상세 왕복마다 | 핵심 기능은 가능 | 읽던 정보 재확인 | 추가 1회 | 낮음: UI 상태 |
| MEDIUM · B/C | 출발 이유가 필수인지 제출 전 알 수 없음 | 새 여정마다 | 복구 가능한 안내창 | 필요한 입력 예측 어려움 | 안내창 복귀 | 낮음: 라벨·ARIA |
| MEDIUM · B/C | 첫 기록 6/6과 실제 동물 누락 상태의 불일치 | 최초 생성 | 최종 누락 버튼으로 복구 가능 | 카드 유형/종 구분 | 누락 단계 왕복 | 중간: 진행률 의미 검토 필요 |

HIGH 세 가지를 우선 구현하고, 같은 탐색 흐름의 상세 유지와 독립적인 필수 라벨 보정을 포함했다. 온보딩의 진행률은 보류했다. LOW 변경은 하지 않았다.

## 5. Changes

### 처방 → 재료 연결

Observed Problem → 요구 태그를 기억해서 도감으로 이동하고, 남아 있는 검색/필터를 해제해야 했다.

Intervention → 펼친 질환 상세의 요구 약효 바로 아래에 기존 `workspace-link`로 “SCALE 영약재 찾기 ↗” 같은 연결을 배치했다. 요구 조건의 기존 구조에서 canonical tag를 추출하고 중복을 제거한다. 링크를 누르면 해당 약효를 선택하고 이전 검색·분류·지역·계절·환자 한정 조건을 정리한다. 기존 `focusCurrentWorkspace`로 결과 요약에 포커스와 스크롤을 연결하고, 요약에도 선택 약효를 표시한다.

Expected Benefit → 다른 화면에서 태그를 다시 고르거나 빈 결과의 원인을 추론하지 않고 해당 재료부터 비교한다. 일반 탐색 버튼은 기존 필터를 유지하며, 이 명시적인 새 검색 동작에서만 조건을 정리한다.

조건의 세기, 조합, 치료 판정은 바꾸지 않았다. 링크는 태그 보유 재료를 찾는 도감 필터이며 처방 충족 여부를 판정하는 버튼이 아니다. 대체 처방의 문장과 비태그 조건도 그대로 유지한다.

### 모바일 작업 복귀

Observed Problem → 찾기 모드로 돌아올 때 항상 첫 목적지인 영약재로 이동했다.

Intervention → `JournalNavigation`이 같은 캠페인 세션에서 모드별 마지막 방문 목적지를 기억하게 했다. 현재 모드를 다시 누르면 현재 페이지를 유지한다. 기존 3모드/9목적지 탐색은 그대로다.

Expected Benefit → 질환을 읽던 사용자가 기록 작업 후 동일한 질환 화면으로 돌아온다. 새로운 메뉴나 목적지를 추가하지 않는다.

### 질환 상세 복귀

Observed Problem → 화면을 왕복하면 이미 읽던 처방이 접혔다.

Intervention → 기존 native details의 열림 상태를 캠페인 UI 상태로 보관한다. 새 캠페인이나 캠페인 교체 시 초기화한다. 검색 조건이 바뀌어 잠시 목록에서 사라지는 경우에도 같은 세션의 열림 상태를 유지한다.

Expected Benefit → 같은 처방의 재펼침과 요구 약효 재탐색이 줄어든다. Enter로 펼치고 접는 기존 동작을 유지한다. 저장 스키마에 필드를 추가하지 않는다.

### 짧은 데스크톱 레일

Observed Problem → flex 축소로 브랜드 설명과 첫 탐색 항목이 겹쳤다.

Intervention → 기존 레일의 브랜드·탐색·정체성 영역에 `flex-shrink: 0`을 적용했다. 기존 세로 스크롤을 사용한다.

Expected Benefit → 첫 목적지와 브랜드가 겹치지 않는다. 짧은 화면에서는 하단 정체성 문구를 스크롤해 읽지만, 주요 9개 목적지는 기존 색인에서 찾을 수 있다. 전체 간격·글꼴·레일 폭은 바꾸지 않았다.

### 출발 이유의 필수성

Observed Problem → 출발 버튼을 누른 뒤에야 이유 입력이 필수임을 알게 됐다.

Intervention → “여정을 떠나는 이유 (필수)” 표시, `htmlFor`/`id` 연결, `aria-required="true"`를 기존 입력에 추가했다. 제출 검증과 저장 처리에는 변화가 없다.

Expected Benefit → 작성 전에 필수 입력을 식별하고 라벨을 눌러 입력란으로 이동한다. 정상 입력 수는 줄이지 않는다. 기존 여정 순서 검사 테스트의 문구도 새 라벨에 맞췄다.

구현 파일: `src/App.tsx`, `src/components/JournalExperience.tsx`, `src/workspace.css`. 테스트 조정: `src/map/mapView.test.ts`. 이번 작업만의 변경은 [calibration.patch](</Users/imwul/Library/Mobile Documents/com~apple~CloudDocs/apawthecaria-apo/output/ux-calibration-evidence/calibration.patch>)에 분리했다. CSS 추가는 축소 방지와 링크 줄바꿈을 위한 2개 규칙이다.

## 6. Preserved Elements

색상, typography, 워드마크, 레일 폭, 주요 grid와 여백 체계, 카드/대장의 정보 밀도, 3그룹과 9개 목적지, 기존 반응형 전환을 유지했다. 새 dashboard, 새로운 카드 체계, 새로운 아이콘·장식·색상 언어를 만들지 않았다.

## 9. Remaining Problems

1. 첫 기록의 “6/6”은 카드 표 선택 수와 실제 필수 입력 완성을 혼동할 수 있다. 누락 복귀는 동작하지만, 진행률의 의미와 카드 유형/실제 종의 안내는 별도 검토가 필요하다. 생성 절차 전체의 범위를 키우지 않기 위해 보류했다.
2. 초기 코드 분할과 큰 App 모듈은 그대로다. 최종 빌드에 500kB 초과 chunk 경고가 남는다. iCloud 개발 파일의 읽기 지연과 최초 로딩을 사용자 환경에서 구분해 측정한 성능 개선은 수행하지 않았다.
3. 모드·펼침 기억은 새로고침까지 영구 보관하지 않는다. 현재 작업 재개 편의를 위해 UI 세션 동안 유지하며, 캠페인 교체 시 다른 기록의 상태가 이어지지 않도록 했다.
4. 치료 완료·조우의 모든 분기, 클라우드 동기화, 전체 백업/복원, 실물 카드 입력의 모든 경우를 실제 브라우저에서 재수행하지 않았다. 관련 기존 자동 테스트는 통과했다.
5. 인간 사용자의 이해도·작업 시간·선호도는 측정하지 않았다. 다음 연구에서는 반복 플레이어에게 자료/기록 왕복 과제를 주고, 모드 기억과 필터 해제의 기대가 일치하는지 확인해야 한다.

### EMPATHIZE — User Insights / Key Observations / Empathy Map

Journey Mapping: 재개 → 현재 절차 확인 → 자료 검색/비교 → 실행 → 결과 → 이야기 → 다음 행동의 여정에서, 처방-도감과 찾기-기록 왕복을 반복 구간으로 선정했다. Role Playing: 플레이어의 작업을 실제 로컬 캠페인에서 직접 수행했다.

Empathy Map의 Do는 관찰이다: 약효를 읽고 다른 화면의 필터를 고름, 모드 복귀 후 질환을 다시 찾음, 초안 작성 중 규칙을 확인함. Think/Feel은 가설이다: “이 결과가 처방에 맞는가?”, “왜 재료가 없지?”, “읽던 곳으로 돌아가고 싶다.” Say는 실제 참가자 발언이 없어 수집하지 않았다. 이는 인터뷰 연구를 대신했다는 주장이 아니다.

### PROTOTYPE — Approach / Description / Features to Test

별도 정적 목업 대신 기존 컴포넌트의 동작을 작게 수정한 실행 가능한 프로토타입을 만들었다. 이 문제는 시각 시안보다 실제 화면 왕복과 상태·포커스를 확인해야 했기 때문이다. 도감 링크의 조건 전달, 모드·상세 복귀, 레일 겹침, 이유 라벨의 의미를 검증 대상으로 정했다.

### TEST — Testing Plan / User Feedback / Key Learnings

Assumption Testing: 링크 한 번이면 이전 조건에 막히지 않고 요구 약효의 재료가 나오는가? 같은 모드로 돌아오면 읽던 상세를 재개하는가? 좁은 화면에서도 결과 조건을 즉시 알 수 있는가? 각 가설을 브라우저의 결과·입력값·열림 상태·포커스로 검증했다.

처음 연결 검증에서는 결과가 화면 아래에 있어 모바일 사용자가 다시 내려가야 했다. 기존 포커스 helper를 결과 요약에 연결하고, 선택 태그를 요약에 표시한 뒤 다시 확인했다. 여정 시작 검증에서 필수 이유를 제출 뒤 알게 되는 문제를 관찰해 라벨만 보정했다. 이 반복은 가설 → 구현 → 실제 행동 → 결과에 따른 수정이다.

User Feedback: 모집된 사용자의 피드백은 없다. 7절의 결과는 에이전트가 수행한 과제 관찰이며 사용자 만족도 결과가 아니다. Key Learnings: 작은 연결·UI 메모리 변경만으로 반복 조작을 줄일 수 있었고, 결과 근처에 현재 조건을 표시해야 모바일에서도 연결의 의미가 보였다.

### Next Steps — Refinements / Action Items / Success Metrics

후속 후보는 첫 기록 진행률 안내와 실제 반복 플레이어 검증이다. 큰 번들 성능은 별도 측정·코드 분할 작업으로 다룬다. 성공 지표는 처방 연결 4→1회, 모바일 복귀 4→2회, 상세 재펼침 1→0회, 브랜드 겹침 42.64→0px, 이야기 반복 입력 0 유지다. 수행하지 않은 연구나 후속 작업을 완료로 표시하지 않았다.
