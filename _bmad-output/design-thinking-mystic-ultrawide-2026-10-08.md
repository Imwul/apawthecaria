**Date:** 2026-10-08
**Facilitator:** Codex, BMAD Creative Intelligence Suite
**Design Challenge:** 룰북의 시각적 세계와 실제 플레이 도구를 함께 살리는 반응형 웹앱.

이번 세션은 이전 룰북 재검토 세션과 구분하여 새 문서에 기록한다. 사용자가 분석부터 구현·검증까지 중간 승인 없이 진행하도록 명시했다. 따라서 스킬의 각 단계 산출물을 저장하면서 자율적으로 다음 단계로 진행한다. 설치된 workflow customization의 prepend/append/persistent facts는 비어 있다.

## Design Challenge

3440px 화면에서 좁은 중앙 대시보드가 떠 있는 인상을 없애고, 작은 약제사가 낯선 숲에서 여행하고 돌보는 룰북의 분위기를 살린다. 장식이 실제 판정, 시간 추적, 규칙 참조를 방해하지 않도록 한다. 모바일에서도 다음 행동과 직접 탐색 도구에 빠르게 접근할 수 있어야 한다.

근거: 사용자의 직접 피드백 “3440 화면 고려”, “룰북 자체의 디자인 고려”, “어딘가 신비로운 느낌이 하나도 없어”; 제공된 220쪽 룰북의 이전 독립적인 전체 재독 결과; 이번 원본 시각 감사; 실제 브라우저 시제품 검증.

## DEFINE: Frame the Problem

### Point of View Statement

숲의 약제사로 혼자 플레이하는 사람에게는 현재 행동과 규칙을 빠르게 대조할 수 있는 일지가 필요하다. 기능의 정확성만으로는 원본의 작고 신비로운 여행 경험을 전달할 수 없기 때문이다.

### How Might We Questions

1. 어두운 숲의 장면과 밝은 읽기 면으로 신비로움을 전달하면서도 조작은 또렷하게 유지할 수 있을까?
2. 3440px의 여유를 긴 문장이 아닌 상태·행동·참조의 동시 배치에 쓸 수 있을까?
3. 원본 삽화를 보존하며 모바일에서는 다음 행동을 먼저 보여줄 수 있을까?
4. 진행·도감·기록·대화상자가 같은 책의 서로 다른 페이지처럼 보이게 할 수 있을까?

### Key Insights

핵심은 색을 어둡게 바꾸는 것만이 아니라 **깊은 숲 바깥, 빛이 닿은 종이 안쪽**의 관계다. 상태와 실제 작업을 같은 높이에 배치하면 넓은 화면의 이점과 펼친 책의 인상을 함께 얻는다. 본문 전체에 장식체를 적용하면 원본의 서체 위계와 플레이 목적을 모두 해친다.

## IDEATE: Generate Solutions

### Selected Methods

**Brainstorming**으로 대안을 펼치고, **Analogous Inspiration**으로 원본의 책·도감·작업대를 읽으며, **SCAMPER Design**으로 기존 대시보드의 배치·질감·불필요한 장식을 교체하거나 제거한다.

### Generated Ideas

1. 어두운 숲을 전체 바깥 장면으로 사용한다.
2. 밝은 종이 위에 실제 판정과 입력을 배치한다.
3. 펼친 책의 왼쪽에는 상태·행동·규칙, 오른쪽에는 현재 절차를 둔다.
4. 3440px에서 작업면 폭을 넓히고 양쪽 숲 여백을 유지한다.
5. 문장 폭은 제한하고 비교표와 입력 면에 넓은 공간을 준다.
6. 원본 표지의 텍스트 없는 그림을 첫 장 삽화로 쓴다.
7. 원본 작업대 그림을 배낭·영약재·규칙·기록의 첫 장에 쓴다.
8. 원본 지하 입구 그림을 지도와 발견 페이지에 쓴다.
9. 약초 무늬를 어두운 탐색 책등에 은은하게 둔다.
10. 금빛 가는 선으로 면과 장을 구분한다.
11. 달·별·작은 식물의 잉크 인장을 장식으로 둔다.
12. 한국어 장 제목에 명조 계열을 제한적으로 사용한다.
13. 본문과 조작은 기존의 명료한 산세리프를 유지한다.
14. 시간 기한에 먹빛 보라, 여행 상태에 숲색을 쓴다.
15. 주 행동 하나를 진한 숲색으로 표시한다.
16. 패널 자체의 폭에 맞춰 조제 도구 비교를 한 열 또는 두 열로 바꾼다.
17. 모바일에서는 첫 장 장식을 숨겨 주요 행동을 밀어내지 않는다.
18. 페이지 넘김 애니메이션을 적용한다.
19. 화면마다 장식 아이콘을 크게 반복한다.
20. 실제 작업과 상태를 별도 스크롤 면으로 만든다.
21. 화면 전체를 어두운 모드로 만든다.
22. 황금빛과 종이색을 대화상자·참조·필터에도 통일한다.

### Top Concepts

세 가지 개념을 결합해 구현한다: **숲 속의 밝은 일지**, **넓은 화면에서 펼친 두 책장**, **원본 삽화와 절제된 잉크 장식**. 18–21은 추가 움직임·반복 장식·이중 스크롤·가독성 비용 때문에 채택하지 않는다. 기존 도구와 판정 흐름은 시각 변화가 필요로 하는 범위 안에서 재배치한다.

## PROTOTYPE: Make Ideas Tangible

### Prototype Approach

**Storyboarding**: 펼친 일지 → 오늘 상태 → 다음 행동 → 오른쪽 판정 면 → 규칙 읽기. **Role Playing**: 검증용 캠페인에서 치료 가능한 환자, 채집이 필요한 환자, 진료 후 출발 상태를 실제 UI로 따라간다. 규칙 엔진을 가짜 동작으로 대체하지 않고 기존 구현을 사용하는 실행 가능한 시제품을 만든다.

### Prototype Description

- `FolioFrontispiece.tsx`: 출처가 기록된 원본 JPEG와 달·식물 인장. 장식은 보조기술에서 숨긴다.
- `mystic-folio.css`: 숲 바깥·종이 안쪽의 색·서체·장식과 3440px 레이아웃. 기존 cascade 뒤에서 적용한다.
- `App.tsx`: 하나의 진행판을 context와 work region으로 나눈다. 개요→행동→규칙→절차의 DOM 순서를 유지한다.
- 원본 JPEG 3종은 PDF의 embedded stream과 바이트가 동일하다. 이미지 편집·재생성·재인코딩을 하지 않았다. 출처는 `public/art/rulebook-art-provenance.md`에 기록했다.

### Key Features to Test

3440×1440, 3440×1080, 중간 데스크톱, 390×844, 320px에서 넘침·첫 행동·규칙 접근·조제 열 수·대화상자·본문 가독성을 확인한다. 시각적 일관성뿐 아니라 판정과 저장·초안 동작을 회귀 확인한다.

## TEST: Validate with Users

### Testing Plan

실제 사용자를 모집한 테스트는 수행하지 않았다. 직접 주어진 불만을 출발점으로, 검증용 기록을 정상 UI에서 불러와 브라우저에서 과제를 수행한다. DOM 폭 측정과 스크린샷으로 구현상 가정을 검증하고, 자동 검사로 기존 규칙 흐름과 레이아웃 계약을 확인한다.

### User Feedback

현재 확인된 피드백은 새 작업을 요청한 사용자의 원본 발언이다. 이번 구현에 대한 새 만족도나 반응을 만들어내지 않는다.

### Key Learnings

- 첫 3440px 시제품: 숲 여백·원본 그림·동시 작업 영역이 보이고 가로 넘침은 없었다.
- 첫 1560px 시제품: 조제 면이 좁아지는데 기존 viewport 기준 두 열이 남았다. work container 기준 840px 이하에서 한 열로 바꾸고 중간 폭 context를 380px로 축소했다.
- 첫 모바일 시제품: 390×844에서 주 행동은 y=773–826에 노출됐다. 장식 첫 장을 숨기는 선택은 첫 행동을 보존했다.
- 기존 더 높은 CSS specificity가 흰색 details 면을 유지했다. 실제 선택자를 맞춰 종이색으로 수정했다.

추가 관찰과 수정:

- 한국어 짧은 제목에는 단어 보존과 줄바꿈 제어를 적용했다. 규칙 링크의 화살표와 “준비 도구”가 따로 줄에 남지 않는다.
- 활성 탐색 버튼의 hover까지 동일한 숲색·금빛 선으로 맞췄다.
- 기존 1050px 이하의 수평 탐색 전환과 새 rail 높이가 충돌할 가능성을 확인하고 같은 breakpoint로 정렬했다. 1024px rail은 182px 높이이며 여섯 도구의 실제 폭은 각각162px이다.
- 참고 규칙을 한 번 눌러 p.32–33 한국어 안내를 읽고, 닫아서 기존 조제 선택으로 돌아왔다. 요구 약효·도구를 만족하는 준비 상태는 유지됐다.
- 390px에서 약재 두 개와 나무 절구를 선택한 뒤 조사↔조제 작업을 전환해도 선택3개와 준비 완료가 유지됐다.

검증 중 iCloud가 node_modules를 반복해서 dataless 상태로 되돌려 초기 검사 시작이 실패했다. 원래 의존성은 프로젝트 밖 같은 CloudDocs 부모에 보존하고, 원본 lock으로 공식 registry에서 복구한 iCloud 밖 캐시의 node_modules를 연결했다. 원본 package/lock/설정 내용은 바꾸지 않았다. 오래된 설정 파일은 brctl로 다운로드하여 실제 byte 수를 확인했다. 원본 PDF를 포함한 사용자 자료는 보존했다. 공간이 부족할 때 이 작업에서 생성한 중간 PDF PNG와 원본 lock의 integrity에 일치하는 재다운로드 가능한 npm 압축 캐시 52.1MB를 정리했다. 설치된 의존성은 유지했다.

원본 전체 검사의 유일 실패는 source-reading 테스트가 iCloud 파일 복원에 36.38초 걸려 제한시간을 넘긴 것이었다. 현재 작업 소스·설정과 필수 root 자료 총 359파일을 iCloud 밖 validation 캐시에 복사하고 각각 SHA-256 일치를 확인했다. 같은 원본 lock·같은 내용·같은 명령의 전체 검사에서 해당 테스트도 통과했다. 환경 파일은 복사하지 않고 빌드 시 원본의 Vite production 환경 값을 메모리에서 전달했다. 캐시의 `working-source-sha256-20261008.json`과 `build-additional-source-sha256.json`에 복사 검증을 기록했다. production output은 프로젝트 `dist`로 복사한 뒤 모든 출력 파일의 SHA-256 일치도 확인했다.
