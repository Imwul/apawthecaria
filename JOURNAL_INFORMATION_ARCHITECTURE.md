# Journal information architecture

The Journal is a campaign memory surface, not a transaction log. Every displayed
field belongs to one of the following layers.

| Layer | Stored/displayed information | Reading priority |
| --- | --- | --- |
| A — Player Memory | Encounter note, custom journal body, player reflection | Primary, verbatim |
| B — Gameplay Event | Resolved choice, treatment/journey outcome, meaningful resource or reputation change | Primary when no memory; otherwise immediately after it |
| C — Context | Location, season, Patient, Journey | Compact supporting metadata |
| D — Source / Provenance | Rulebook page, canonical source title/prompt and available printed choices | Closed by default; available on demand |
| E — Internal / Debug | Transaction IDs, choice IDs, raw enums, low-level state confirmations | Never shown in the normal Journal |

## Existing data paths

- Player-created entries already have a trustworthy boundary: `title` and `text`
  are both authored by the player. Their text must never be translated or
  rewritten.
- Recent Encounter entries use labelled sections inside one concatenated string
  (`나의 기록`, `조우 정보`, `조우 맥락`). These labels are safe to parse because
  the application produced them. New Encounter entries should use structured
  fields instead.
- Older Encounter entries may use the exact application delimiter `나의 선택`.
  Only that exact format may be separated. Unrecognised legacy text remains
  intact.
- Engine journal events carry a semantic `type`, but the UI's `JournalEntry`
  model currently drops that type. The adapter from engine events to Journal
  entries is the correct place to retain event semantics, localise player-facing
  outcome text, and mark low-level progress records.
- Manual-effect records contain a reliable source header generated by the
  application. New records should store memory, result, and provenance
  separately; old unmatched strings must remain untouched.

## Presentation contract

1. Player Memory is shown first and verbatim.
2. The event that actually happened follows; unchosen options do not compete
   with the result.
3. Context is concise and only rendered when present.
4. Source / Provenance is available through progressive disclosure.
5. Internal IDs and implementation-only events are excluded from normal reading.
6. Recent previews choose Player Memory, then Gameplay Event, then useful
   Context. They never derive a preview from raw source payloads.
